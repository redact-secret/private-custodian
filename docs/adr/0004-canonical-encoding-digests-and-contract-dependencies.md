# 0004. Canonical encoding, digests, domain separation, time and contract dependencies

- Status: accepted (design baseline)
- Date: 2026-10-02
- Deciders (by role): repository maintainer (single human operator)
- Maintenance: this repository is maintained by the Redact Secret project; decisions here are
  project-maintained, not independent validation.

## Context

ADR 0002 left canonical serialization and digest rules to C2. C3 to C9 and the sibling repositories
(engines, benchmarks) must hash, sign and verify the same bytes without sharing code. Contracts carry
untrusted input from the request edge, the worker and public consumers, so the encoding must be strict,
bounded and unambiguous (CONVENTIONS.md, "Identity and transitions"). `custodian-core` stays std-only.

## Options

| Choice | Alternatives considered |
| --- | --- |
| Encoding | canonical JSON (RFC 8785 subset); CBOR deterministic (RFC 8949 4.2); protobuf; defer |
| Digest | SHA-256 with domain prefix; SHA-256 plain; BLAKE3; HMAC for all |
| Time | integer seconds since the Unix epoch; RFC 3339 strings; logical counters |
| Schemas | generated from Rust types and checked in with a drift test; hand-written; generated only |
| Dependencies | std only (hand-rolled JSON, SHA-256); pinned `serde`, `serde_json`, `sha2`, `schemars` in `custodian-contracts` only |

Criteria: byte-for-byte reproducibility in other languages (benchmarks is TypeScript), small attack
surface, strict rejection of ambiguity, reviewability, and not putting parsing code of our own on the
trust boundary.

## Decision

1. **Encoding: `custodian-canonical-json/1`.** A strict subset of RFC 8785 (JCS). Compact JSON; object
   members sorted by key; integers only, `0..=2^53-1`, no sign, fraction or exponent; strings restricted to
   printable ASCII (`0x20..=0x7e`) without `"` or `\`; no `null`; absent optional fields are omitted. Within
   that subset the output equals JCS output, so any RFC 8785 implementation reproduces it. The subset
   exists so canonicalization needs no Unicode normalization or number formatting, the two usual sources of
   cross-language disagreement. Non-ASCII, floats and nulls are rejected, not normalized.
2. **Strict decoding.** `Contract::decode` enforces, in order: a 65,536-byte cap before parsing; a typed
   parse with `deny_unknown_fields`, duplicate-field rejection, fixed schema tag, bounded strings, bounded
   integers and bounded arrays; then document-level `validate`. `decode_canonical` additionally requires the
   input bytes to equal the canonical encoding and is the entry point for anything hashed or verified.
   Errors are fixed enums that never echo input.
3. **Digest construction.** `digest = SHA-256( domain || 0x00 || canonical_bytes )`, rendered as
   `sha256:` plus 64 lowercase hex characters. Domain tags are in `canonical::DomainTag`
   (`private-custodian/v1/<document>`): request, plan, approval, reservation, execution, internal-receipt,
   public-projection, revocation-envelope, policy-activation. Tags contain no NUL, so the concatenation is
   unambiguous. A tag is never edited; a new rule is a new tag.
4. **Signing input.** A signature covers exactly the same `domain || 0x00 || canonical_bytes` string of the
   enclosed payload. An envelope is `{payload, signature}`; the signature is not part of the signed bytes.
   Signature algorithm, key provider, rotation and verification are C7. `Ed25519` is the only algorithm
   named in v1 and C7 may change it before any receipt is issued, through a new schema version.
5. **Candidate and artifact digests are plain SHA-256** of the exact staged bytes (no domain prefix), so
   they can be checked with any SHA-256 tool and by parties that never run this code. They are typed
   separately (`CandidateDigest`, `ArtifactDigest`, `ConfigDigest`, `ResultDigest`, `PopulationDigest`)
   from domain-separated document digests (`PlanDigest`, `ProjectionDigest`, `DocumentDigest`).
6. **Identities.** Opaque, random, prefixed (`req_`, `idk_`, `apr_`, `rsv_`, `exe_`, `rcp_`, `prj_`, `act_`,
   `cor_`, `epo_`, `fam_`, `lin_`, `pac_`, `ppr_`, `fed_`, `key_`), 16 to 64 lowercase alphanumerics after the
   prefix. They are URL-safe, independent of scanner versions, and not derived from content. A wrong-type
   identity fails to parse. `custodian-core` keeps its opaque `String` identities; adapters convert at the
   boundary.
7. **Time.** `Timestamp` is an integer count of seconds since the Unix epoch (UTC). Contracts carry no
   clock: the control service passes `now` into every check. The core's logical `expires_at: u64` is that
   same unit. Sub-second precision is not needed for approvals, leases or freshness windows. A clock
   that moves backwards is handled by failing closed: state observed in the future is stale.
8. **Schemas.** Rust types are the source. JSON Schemas (draft 2020-12) are generated by `schemars`, with
   null alternatives removed, and checked in at `crates/custodian-contracts/schemas/v1/`. A drift test
   fails if the files differ from generated output; structural tests fail if any object is open or any
   string, array or integer is unbounded. The Rust decoder is the executable specification; the schemas
   are the interchange description for other languages (C11 should validate them with a schema validator in
   the consumer).
9. **Dependencies.** `serde`, `serde_json`, `sha2` and `schemars` are added to `custodian-contracts` only,
   pinned with exact versions in `Cargo.toml` and committed in `Cargo.lock`. `custodian-core` remains
   std-only. Rationale: parsing untrusted JSON and SHA-256 are the two things least wise to hand-roll;
   these are widely reviewed crates, and `schemars` is used only to emit schemas and in tests. Upgrades are
   deliberate, reviewed changes; `cargo test --locked` in CI refuses an unreviewed lock change.

## Security properties claimed

All claims are for the contract layer only; no signer, store or service exists yet.

| Property | Test |
| --- | --- |
| Unknown, duplicate, oversized or out-of-bound input rejected | `tests/negative.rs` |
| Non-canonical bytes rejected where canonical is required | `decode_canonical_rejects_non_canonical_bytes` |
| Encoding and digests are stable | `tests/golden.rs`, including an independent `shasum` cross-check |
| Same payload under another domain gives another digest or signing input | `domain_separation_is_effective` |
| Every material plan field changes the plan digest | `plan_digest_binds_every_material_field` |
| Public schemas are closed, bounded and free of forbidden fields and hash shapes | `tests/schemas.rs` |

A digest or a signature proves integrity and origin of bytes, not truth of their content.

## Adapter contract

Contracts are pure data and pure checks: no I/O, no clock, no key, no store. Adapters (C3 intake, C4 store,
C7 signer) call `decode`, `canonical_bytes`, `document_digest`, `signing_input` and the `check_*`
functions, and supply `now`.

## Failure and recovery

Any parse, bound, binding or freshness failure is a rejection with a fixed code; nothing is repaired or
defaulted. Unknown schema versions are rejected, never coerced. A document that cannot be canonicalized
cannot be hashed or signed.

## Performance evidence plan

Canonicalization allocates a `serde_json::Value` per document, capped at 64 KiB. C4 and C7 measure decode,
canonicalize and hash cost inside transaction and export latency; no check is relaxed for speed.

## Consequences, migration, exit

Moving to another encoding means new domain tags and schema majors; old digests stay valid for old
documents. The ASCII-only string rule means a future need for non-ASCII text is a schema revision, which
is intended: contracts carry identifiers and enumerations, not prose.

## Open risks and revisit triggers

Cross-language canonicalization is claimed from the JCS subset and the golden vectors, but no second
implementation exists yet (C11 should add one in the benchmark consumer and run the vectors). The 2^53
integer cap bounds counts and timestamps. `schemars` output formatting could change on upgrade; the drift
test makes that visible. Revisit if a contract needs floats, non-ASCII text or documents above 64 KiB.
