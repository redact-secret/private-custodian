# 0112. Signer key provider contract, key file rules and process hardening

- Status: accepted (design); implemented in `crates/custodian-signer` (S2); not deployed
- Date: 2026-10-03
- Deciders (by role): project maintainer
- Maintenance: this repository is maintained by the Redact Secret project; its decisions are
  project-maintained, not independent validation.

## Context

ADR 0050 left the key provider to deployment. SECURITY.md requires signing keys in an approved runtime
provider with defined rotation and revocation, and ADR 0101 fixes operating constraints for rotation. The
signer needs a way to obtain its key that can be tested with synthetic keys, refuses to run on a careless
setup, and does not leak the key through logs, errors, child processes or core dumps. No production key exists
and none may be generated or committed by this repository.

## Options

| Choice | Alternatives considered |
| --- | --- |
| Provider interface | A trait the signer calls (`KeyProvider`); a path argument only; environment variable; defer to KMS |
| First provider | Owner-only key file; OS keystore; KMS or HSM; key generated by the signer on first start |
| Key format | 64 lowercase hex characters (one optional newline); raw 32 bytes; PEM/PKCS#8 |
| Hardening | `setrlimit` core 0 + non-dumpable + env scrub + umask; none; seccomp/landlock sandbox |

Criteria: a key never appears in argv or the environment, the file checks are TOCTOU-resistant with std only,
operators can provision by hand, and a future KMS or HSM provider needs no signer change.

## Decision

1. **`KeyProvider::load_seed() -> Result<SecretSeed, KeyProviderError>`** is the only way the signer gets key
   material. `KeyProviderError` has a fixed vocabulary (`key_not_found`, `key_directory_insecure`,
   `key_not_regular_file`, `key_hard_linked`, `key_wrong_owner`, `key_permissions_insecure`, `key_file_raced`,
   `key_malformed`, `key_provider_unavailable`) and never names a path or carries bytes. A KMS or HSM provider
   that signs without exporting the seed would need a signing-oriented trait; that is a future ADR and is not
   pretended here.
2. **`FileKeyProvider`** (test keys in this repository; production provisioning stays manual). It refuses
   unless: the immediate directory is a real directory (not a symlink) owned by the signer's effective uid with
   no group or other access; the key path is a regular file (not a symlink, socket or device) with exactly one
   link, owned by the effective uid, with no group or other access and no execute bit (0600 or 0400); the file
   that was opened has the same device and inode as the one checked; and the content is exactly 64 lowercase
   hex characters with at most one trailing newline. Ancestors above the immediate directory are not checked;
   that is a deployment obligation.
3. **`SecretSeed`** has a redacting `Debug`, no `Display`, `Clone`, `Serialize` or `PartialEq`, and zeroizes
   its bytes on drop. The read buffer is zeroized. The seed is copied into the signing key (zeroized on drop by
   `ed25519-dalek`) and the provider's copy is dropped before the server starts. `SigningEngine`,
   `RunningServer`, `FileKeyProvider` and `UnixSocketTransport` have `Debug` that omits keys and paths.
4. **Logs and errors** carry fixed codes only: no payload text, no path, no key id beyond configuration the
   operator wrote, no key bytes. The binary prints `custodian-signer: <code>` lines to stderr and the public
   key (only on `--print-public-key`) to stdout.
5. **Process hardening** before the key is read: `RLIMIT_CORE` soft and hard set to 0 (refuse to start if that
   fails); on Linux `PR_SET_DUMPABLE=0`, which also keeps same-uid processes out of `/proc/<pid>/mem` and
   `environ` and blocks same-uid ptrace; `umask 077`; every environment variable removed. The signer starts no
   child process, and every file it opens is `O_CLOEXEC` (the Rust default), so no key descriptor can be
   inherited.
6. **Key window.** The configuration carries `valid_from` and an optional `not_after`. The signer uses the key
   only inside `[valid_from, not_after)` by its own clock and otherwise answers `sign_signer_unavailable` (its
   own event stream says `key_out_of_window`). This mirrors the verifier's `KeyEntry` window (ADR 0050, ADR
   0101) so a retired key stops signing even if the control service is stale. Rotation follows ADR 0101: the
   new key is generated on the signer host, its public half published by a signed key event, and the old key's
   window ended.
7. **Provisioning is manual and on the signer host only.** The key is generated there with `umask 077`, never
   copied to the control host, never committed, never placed in GitHub Actions. `--print-public-key` gives the
   operator the public half to pin as a verifier root.

## Security properties claimed

| Property | Failure test |
| --- | --- |
| Owner-only key in an owner-only directory loads; group/other/exec bits, open directories, symlinks, hard links, sockets, missing and malformed files are refused | `tests/provider.rs` (`an_owner_only_key_in_an_owner_only_directory_loads`, `group_other_and_executable_bits_are_refused`, `an_open_directory_is_refused`, `symlinks_hard_links_sockets_and_missing_files_are_refused`, `only_exactly_64_lowercase_hex_characters_are_accepted`) |
| Errors never name a path or key bytes | `provider_errors_name_neither_paths_nor_key_bytes` |
| No key material, path or client text in responses, events, errors, Debug output or the binary's stderr | `tests/signer.rs::no_key_material_or_payload_text_appears_in_responses_events_errors_or_debug`, `tests/process.rs::the_binary_signs_survives_kill_and_restart_and_logs_only_fixed_codes` |
| The binary refuses to start on an insecure key, directory, config or arguments | `tests/process.rs::the_binary_refuses_to_start_on_insecure_keys_configs_and_arguments` |
| Core dumps off, environment cleared, umask restricted | `tests/provider.rs::hardening_applies_in_a_child_process` |
| On Linux the running signer is non-dumpable: core limit 0 and `/proc/<pid>/mem`, `environ` unreadable to a same-uid reader | `tests/process.rs::linux_process_boundary_keeps_same_uid_readers_out_of_signer_memory` (runs in the CI `rust` job on Linux) |
| A key outside its window does not sign | `tests/signer.rs::a_key_outside_its_window_does_not_sign` |

"The control service cannot read the key" is enforced by file ownership and mode plus the uid separation the
deployment provides; these tests prove the signer refuses a key file that other uids could read and that the
running process is not readable by a same-uid peer on Linux. They cannot prove a deployment's uid layout.

## Adapter contract

`KeyProvider` (above). `SignerSetup` (key id, purposes, window, skew) is plain data the configuration builds.

## Failure and recovery

Provider failure at start: the process exits 3 with the fixed code and serves nothing. A key file changed
while running is not re-read; the operator restarts the signer. Compromise: revoke from another key, publish a
new key, re-issue (ADR 0050, ADR 0101; R-4 remains a blocker for recovery tooling).

## Performance evidence plan

Key loading happens once at start; no measurement needed.

## Consequences, migration, exit

Adding a provider is a new implementation; a signing-oriented provider that never exposes the seed needs a new
trait and ADR. Changing the key file format is a new format version the provider must refuse to guess.

## Open risks and revisit triggers

- No `mlock`: key pages can be swapped. Deployments should use encrypted swap or none.
- Ownership by a different uid cannot be tested without root; `key_wrong_owner` is covered by code review and
  the deployment checklist, not by a test here.
- macOS has no `PR_SET_DUMPABLE` equivalent used here; see docs/signer.md for what is and is not enforced.
