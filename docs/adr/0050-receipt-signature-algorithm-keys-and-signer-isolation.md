# 0050. Receipt signature algorithm, key identifiers, key lifecycle and signer isolation

- Status: accepted (design); implemented in `crates/custodian-ledger` (C7); not deployed
- Date: 2026-10-02
- Deciders (by role): project maintainer
- Maintenance: this repository is maintained by the Redact Secret project; its decisions are
  project-maintained, not independent validation.

## Context

ADR 0004 fixed the signing input (`domain || 0x00 || canonical_bytes`) and named `Ed25519` as a
placeholder that C7 may change before any receipt is issued. SECURITY.md requires separate access scopes
for receipt signing, keys in an approved runtime provider, defined rotation and revocation, and a public
verifier that needs no private key. ARCHITECTURE.md requires a signer that accepts only validated approved
projections and is isolated from scanner and agent execution. No receipt has been issued and no key exists.

## Options

| Choice | Alternatives considered |
| --- | --- |
| Algorithm | Ed25519; ECDSA P-256; RSA-PSS; HMAC (shared secret); defer |
| Library | `ed25519-dalek` 2.2.0; `ed25519-dalek` 3.0.0; `ring`; OpenSSL bindings; hand-written |
| Key custody | key provider behind a separate signer process; key file readable by the control service; key in the agent runtime |
| Rotation | out-of-band pinned roots plus signed key events in the ledger; a published JWKS-style URL; no rotation |

Criteria: deterministic signatures (so an export retry produces identical bytes), no shared secret on the
verifier, small reviewed code, independence from OpenSSL builds, and verifiability with a stock tool in
another language (the benchmark consumer is TypeScript).

## Decision

1. **Algorithm: Ed25519 (RFC 8032), confirmed.** The placeholder in `SignatureAlgorithm` stays, so no
   contract schema change is needed. Signatures are 64 bytes, base64url without padding (86 characters),
   matching `SignatureValue`. Verification uses strict checks (`verify_strict`: rejects small-order keys and
   non-canonical encodings). Signatures are deterministic, so identical input gives identical bytes. A second
   algorithm requires a new enum value, a new schema version and a new key purpose; verifiers reject any
   algorithm they do not know.
2. **Library: `ed25519-dalek` pinned `=2.2.0`**, `default-features = false` with `std`, `fast`, `zeroize`.
   Pure Rust, no RNG feature enabled (keys come from a key provider, never generated by this crate), key
   material zeroized on drop. `=3.0.0` exists and needs a newer compiler; 2.2.0 is the long-lived line and
   what other Rust consumers can reproduce, so the upgrade is a deliberate later change. `ring` was not
   chosen because it brings a larger C/asm surface for one primitive. The pin is exact and `Cargo.lock` is
   committed. `serde`, `serde_json` and `sha2` reuse the versions `custodian-contracts` pins.
3. **Key identifiers.** A key id is the existing `key_` identity (`KeyId`): a name, never key material. A
   `Signature` carries `{key_id, algorithm, value}`. The verifier resolves the id in its keyring; an unknown
   id is rejected, never fetched.
4. **Domain separation per document type.** `SignDomain` has one tag per document type: the contracts' tags
   for `public-projection` and `revocation-envelope`, and `private-custodian/v1/ledger/<type>` for each ledger
   record type (audit-event, store-checkpoint, registry-checkpoint, policy, publication, reconciliation,
   key-event). Each key carries a set of purposes (domains); a key is accepted only for its purposes, so
   compromise of a ledger-only key does not allow forging public projections.
5. **Approved-payload gate.** A signer accepts only an `ApprovedPayload`, which is built by decoding the
   canonical bytes as the document type of the domain, running its validation, and for a public projection
   additionally matching a current release approval (`Approval::check_for_release`: exact projection digest,
   execution, disclosure policy, non-agent approver, time window, activation freshness). Refusals use fixed
   codes (`sign_wrong_domain`, `sign_payload_invalid`, `sign_schema_mismatch`, `sign_not_approved`,
   `sign_unknown_domain`, `sign_signer_unavailable`) and never echo the payload.
6. **Isolated signer.** The key lives only in a separate signer process. The control service holds a
   `RemoteSigner` (a key id and a transport) and no key. The signer process runs `SignerService`, which
   re-decodes the wire request with `ApprovedPayload::from_wire`, so it does not trust the caller's
   validation. The wire request is bounded canonical JSON `{domain, payload (base64url), release_digest?}`;
   the response is a `Signature` or a fixed refusal code. The transport (a local Unix socket with peer
   credential checks, owner-only) and the key provider (OS keystore, HSM or a secrets manager reachable only
   by the signer identity) are deployment choices recorded under C12; `SoftwareSigner` exists for tests and
   for the signer process itself. Workers, agents and the request-facing App never hold or reach the key.
7. **Key lifecycle.** The verifier starts from pinned root keys obtained out of band. Further keys arrive as
   signed `key-event` ledger records: `published` (public key, purposes, valid from), `retired` (signatures
   issued at or after the time are invalid, earlier ones stay valid), `revoked` (every signature by the key is
   rejected whenever issued). A key event must verify under a key the keyring already trusts for the
   `key-event` purpose, so rotation is a chain of trust from the roots. Weak (small-order) public keys are
   refused at publication. Recovery from a compromised key: revoke it from another key, publish a new key,
   and re-issue affected records as superseding records signed by the new key.

## Security properties claimed

| Property | Failure test |
| --- | --- |
| Invalid, foreign and edited signatures are rejected | `tests/signing.rs::invalid_and_foreign_signatures_are_rejected`, `tampered_payload_fails_verification` |
| Unknown key id is rejected | `unknown_key_id_is_rejected` |
| A signature under one domain never verifies under another; key purposes scope signing and verifying | `wrong_domain_is_rejected_by_signer_key_scope_and_by_verifier` |
| The signer refuses unapproved, expired, mismatched or modified projections | `signer_refuses_unapproved_or_mismatched_projections` |
| Wire input is re-validated: wrong schema or version, non-canonical bytes, unknown domain, domain mismatch, missing approval | `from_wire_refuses_wrong_schema_domain_encoding_and_missing_approval` |
| Retired keys keep old signatures valid; revoked keys do not | `revoked_key_signatures_are_rejected_and_retired_keys_keep_old_signatures` |
| Rotation is a chain of trust from pinned roots; unauthorised key events are refused | `key_rotation_is_a_chain_of_trust_from_the_pinned_root`, `unsupported_algorithm_and_bad_public_key_are_rejected` |
| The isolated signer protocol signs only validated payloads and the client holds no key | `isolated_signer_protocol_signs_validated_payloads_and_refuses_the_rest`, `remote_signature_verifies_under_the_service_public_key` |
| Signer debug output never shows key material | `software_signer_debug_output_never_shows_key_material` |

A signature attests origin and binding of bytes, not the truth of their content, an independent reviewer or
scanner quality.

## Adapter contract

`Signer` (`key_id`, `sign(&ApprovedPayload) -> Result<Signature, SignRefusal>`) and `SignerTransport`
(`call(request) -> response`). Verification is `Verifier` over a `Keyring`, with public keys only.

## Failure and recovery

Signer unreachable: `sign_signer_unavailable`; the exporter treats it as an error, nothing is written or
acked, and the outbox keeps the event. Key unavailable at the provider: same. A response that names another
key id is refused. No fallback key exists.

## Performance evidence plan

Measure sign and verify latency inside export latency (one signature per record). Do not skip the exporter's
self-verification to save time.

## Consequences, migration, exit

Moving to another algorithm is a new schema version and new key purposes; old records stay valid under old
keys. A change to which actor may approve a release or sign is a signer policy revision, not a code default.

## Open risks and revisit triggers

Software test keys and the in-process loopback prove mechanism, not isolation. Isolation of the signer
process and the key provider is unproven until C12. Retirement relies on the signed document's own
`issued_at`, so a holder of a retired key could back-date; use revocation for compromise. Revisit when
moving to `ed25519-dalek` 3.x or when an HSM-backed signer is chosen.
